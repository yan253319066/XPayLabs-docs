## Authentication Issues

Authentication errors are almost always caused by a missing, malformed, or mismatched API key. Check the points below before assuming an infrastructure problem.

### 401 Unauthorized

A `401` response means the API could not authenticate your request. The most common causes are:

- **No `Authorization` header:** every request to `https://api.xpaylabs.com/v1` must include the header.
- **Incorrect format:** the header value must be `Bearer ` followed immediately by your secret key — no extra spaces, quotes, or newline characters.
- **Revoked or deleted key:** confirm that the key still exists in **Dashboard → Developers → API Keys**.

Make sure your request header looks exactly like this:

```bash
Authorization: Bearer sk_test_YOUR_KEY
```

A minimal authenticated request looks like:

```bash
curl -X GET https://api.xpaylabs.com/v1/payment_intents \
  -H "Authorization: Bearer sk_test_YOUR_KEY"
```

<Warning>
  Never include your secret key in client-side JavaScript or mobile app source code. Use your **publishable key** (`pk_test_` / `pk_live_`) on the frontend and keep your secret key exclusively on your server.
</Warning>

### Using a Test Key in Live Mode (or Vice Versa)

XPayLabs enforces a strict separation between test and live environments. Using a test key against live resources — or a live key while running integration tests — results in a `401` or `403` error.

Check the prefix of the key you are using:

| Prefix | Environment |
|---|---|
| `sk_test_` | Test mode (sandbox) |
| `sk_live_` | Live mode (production) |
| `pk_test_` | Test mode (client-side) |
| `pk_live_` | Live mode (client-side) |

Confirm which environment your Dashboard is currently viewing by checking the **Test Mode** toggle in the top navigation bar. Your API keys, payment records, and webhook endpoints are scoped to either test or live — they do not cross over.

## Payment Failures

When a payment fails, the XPayLabs API always returns a structured error object. Read the `error.code` field to identify the exact cause and surface a clear message to your customer.

### `card_declined`

The card issuer rejected the charge. This is a customer-side issue — your integration has no way to override it. Ask the customer to try a different card or contact their bank.

```json
{
  "error": {
    "type": "card_error",
    "code": "card_declined",
    "message": "Your card was declined.",
    "payment_intent": "pi_abc123"
  }
}
```

In your checkout UI, display a friendly message such as _"Your card was declined. Please try a different payment method."_ Do not surface the raw API message.

### `insufficient_funds`

The customer's account does not have enough balance to cover the charge. This is also a customer-side issue. Prompt the customer to use a different card or payment method.

```json
{
  "error": {
    "type": "card_error",
    "code": "insufficient_funds",
    "message": "Your card has insufficient funds.",
    "payment_intent": "pi_abc123"
  }
}
```

### `invalid_request_error`

This error indicates a problem with the data your server sent to the API — it is an integration bug, not a customer-side issue. Check the `message` field for details.

```json
{
  "error": {
    "type": "invalid_request_error",
    "code": "parameter_invalid",
    "message": "amount must be greater than 0",
    "param": "amount"
  }
}
```

Common causes of `invalid_request_error`:

- **`amount` is zero or negative:** the `amount` field must be a positive integer greater than `0`.
- **`currency` is not a valid ISO 4217 code:** use lowercase three-letter codes such as `usd`, `eur`, or `gbp`.
- **Missing required fields:** `amount`, `currency`, and `payment_method` are all required to create a payment intent.

### Amount in Wrong Units

<Warning>
  All amounts in the XPayLabs API are expressed in the **smallest currency unit**. For currencies with two decimal places (USD, EUR, GBP), this means **cents** — not dollars. A charge of **$25.00** must be sent as `"amount": 2500`.
</Warning>

```json
{
  "amount": 2500,
  "currency": "usd",
  "payment_method": "pm_card_visa"
}
```

Zero-decimal currencies (such as JPY) are an exception — for these, pass the face value directly (e.g., ¥500 → `"amount": 500`). See the [Currencies reference](https://xpaylabs.com/docs/currencies) for a full list.

## Webhook Problems

Webhooks are the primary mechanism XPayLabs uses to push real-time event notifications to your server. The most common issues are misconfigured endpoints, incorrect signature verification, and unhandled duplicate events.

### Not Receiving Webhooks

If your endpoint is not receiving events, work through the following checks:

1. **Endpoint URL is publicly accessible:** XPayLabs cannot deliver webhooks to `localhost` or private network addresses. During local development, use a tunnelling tool such as [ngrok](https://ngrok.com) to expose your local server.
2. **Endpoint responds with HTTP 2xx:** XPayLabs considers a delivery successful only when your endpoint returns a `200`–`299` status code within **30 seconds**. Any other response or a timeout is treated as a failed delivery.
3. **Check the Dashboard delivery log:** go to **Dashboard → Developers → Webhooks**, select your endpoint, and inspect the **Recent Deliveries** tab. Failed deliveries show the HTTP status code and response body your server returned.

<Tip>
  Use the **Send test event** button in the Dashboard to trigger a sample event to your endpoint and verify end-to-end delivery without needing to create a real payment.
</Tip>

### Signature Verification Failing

If your signature check is returning a mismatch, the most likely causes are:

- **Parsing the body before verification:** you must compute the HMAC over the **raw request bytes**, not the parsed JSON object. Parsing changes whitespace and key ordering.
- **Wrong webhook secret:** each endpoint has its own secret. Confirm you are reading the secret for the specific endpoint receiving the event, not a secret from a different endpoint.
- **Encoding mismatch:** ensure your HMAC is computed with UTF-8 encoded bytes and compared as a lowercase hex string.

```python
import hmac
import hashlib
from flask import Flask, request, abort

app = Flask(__name__)
WEBHOOK_SECRET = "whsec_YOUR_ENDPOINT_SECRET"

@app.route("/webhook", methods=["POST"])
def handle_webhook():
    raw_body = request.get_data()  # raw bytes — do NOT call request.json here
    signature = request.headers.get("X-XPayLabs-Signature", "")

    expected = hmac.new(
        WEBHOOK_SECRET.encode("utf-8"),
        raw_body,
        hashlib.sha256
    ).hexdigest()

    if not hmac.compare_digest(expected, signature):
        abort(400, "Invalid signature")

    event = request.get_json()
    # process event...
    return "", 200
```

### Receiving Duplicate Events

XPayLabs delivers each event **at least once**, which means your endpoint may occasionally receive the same event more than once — for example, if your server times out before returning a `200` response.

Protect against duplicate processing by storing each event's `id` and skipping events you have already handled:

```python
processed_event_ids = set()  # use a persistent store (database) in production

@app.route("/webhook", methods=["POST"])
def handle_webhook():
    # ... signature verification above ...
    event = request.get_json()
    event_id = event["id"]

    if event_id in processed_event_ids:
        return "", 200  # already handled — acknowledge and skip

    processed_event_ids.add(event_id)
    # process event...
    return "", 200
```

### Inspecting Webhook Delivery Logs

The Dashboard provides a full delivery history for every webhook endpoint:

1. Go to **Dashboard → Developers → Webhooks**.
2. Click the endpoint URL you want to inspect.
3. Open the **Recent Deliveries** tab to see every attempted delivery, including the HTTP status your server returned, the request headers XPayLabs sent, and the response body.
4. Click **Retry** next to any failed delivery to resend it immediately.

## Settlement Delays

Most settlement delays have a straightforward cause. Check the following before contacting support.

### Account Not Fully Verified

Payouts are blocked until your identity and bank account verification are complete. Go to **Settings → Verification** in the Dashboard to see any outstanding requirements. If a document upload is marked as rejected, re-upload a clearer image and allow 1–2 business days for re-review.

### Public Holiday Buffer

The default T+2 settlement schedule counts **business days only** — weekends and public holidays in your country of operation do not count. A payment captured on the Thursday before a long weekend may not settle until the following week. Review the [Public Holiday Calendar](https://xpaylabs.com/docs/holidays) in the documentation for your country.

### Suspicious Activity Review

If our risk systems detect unusual patterns — such as a sudden spike in transaction volume or an elevated refund rate — your payouts may be paused pending a review. You will receive an email explaining the hold. Respond promptly to any requests for information to minimise the delay. If you believe the hold was applied in error, contact [support@xpaylabs.com](mailto:support@xpaylabs.com) with your account ID and a description of your recent activity.

<Warning>
  Do not create a second XPayLabs account to work around a payout hold. Doing so violates the Terms of Service and may result in permanent account termination.
</Warning>

## Rate Limits

XPayLabs enforces rate limits to ensure fair access and platform stability for all users.

### 429 Too Many Requests

The default rate limit is **100 requests per second per API key**. When you exceed this limit, the API returns a `429` status code. Implement **exponential backoff with jitter** to retry requests gracefully:

```python
import time
import random
import requests

def post_with_backoff(url: str, headers: dict, payload: dict, max_retries: int = 5):
    for attempt in range(max_retries):
        response = requests.post(url, headers=headers, json=payload)

        if response.status_code != 429:
            return response

        # Exponential backoff: 1s, 2s, 4s, 8s, 16s — plus random jitter
        wait_seconds = (2 ** attempt) + random.uniform(0, 1)
        print(f"Rate limited. Retrying in {wait_seconds:.2f}s (attempt {attempt + 1}/{max_retries})")
        time.sleep(wait_seconds)

    raise RuntimeError("Max retries exceeded after repeated 429 responses")
```

### Reading Your Remaining Quota

Every API response includes rate limit headers you can use to monitor your current usage before hitting the limit:

```bash
X-RateLimit-Limit: 100
X-RateLimit-Remaining: 43
X-RateLimit-Reset: 1718123456
```

| Header | Description |
|---|---|
| `X-RateLimit-Limit` | Total requests allowed per second for your key |
| `X-RateLimit-Remaining` | Requests remaining in the current one-second window |
| `X-RateLimit-Reset` | Unix timestamp (UTC) when the current window resets |

If `X-RateLimit-Remaining` drops near zero, throttle your requests proactively rather than waiting for a `429`.

### Increasing Your Rate Limit

If your integration consistently hits the default limit and exponential backoff is not sufficient, contact [support@xpaylabs.com](mailto:support@xpaylabs.com) to request a higher limit for your account. Include your account ID and a description of your expected request pattern.
