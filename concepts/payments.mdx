A Payment object is the core building block of the XPayLabs platform. Every time a customer submits their payment details, XPayLabs creates a Payment object that tracks the full lifecycle of that transaction — from the initial authorization request through processing, confirmation, and eventual settlement to your bank account. Understanding how payments are structured and how they move through states helps you build reliable integrations and handle edge cases gracefully.

## Payment Lifecycle

Every payment moves through a defined sequence of states from the moment it is initiated until the funds are settled into your account. The diagram below describes each stage in that journey.

<Steps>
  <Step title="Initiated">
    Your server calls `POST /v1/payments` with the amount, currency, and payment method. XPayLabs creates a Payment object with status `pending` and returns it immediately.
  </Step>
  <Step title="Processing">
    XPayLabs submits the authorization request to the card network or payment processor. The payment status moves to `processing`. This step typically completes in seconds but may take longer depending on the payment method.
  </Step>
  <Step title="Succeeded or Failed">
    The processor returns an approval or decline. A successful authorization moves the payment to `succeeded`. A decline, network error, or fraud signal moves it to `failed`. At this point, funds are authorized (reserved) on the customer's account.
  </Step>
  <Step title="Settled">
    XPayLabs batches authorized payments and submits them for capture and settlement. Once settled, the net proceeds are transferred to your configured bank account. The payment's `settlement_id` field is populated with a reference to the corresponding settlement batch.
  </Step>
</Steps>

## Payment Statuses

XPayLabs assigns one of the following statuses to every Payment object at any given moment. You can read the current status from the `status` field of the payment response or listen for status changes via webhooks.

| Status | Description |
|---|---|
| `pending` | The payment has been created but has not yet been submitted to the payment processor. |
| `processing` | XPayLabs has submitted the payment and is waiting for a response from the processor or card network. |
| `succeeded` | The payment was authorized and captured successfully. Funds are reserved and will be settled. |
| `failed` | The payment was declined or encountered an error during processing. No funds were captured. |
| `canceled` | The payment was explicitly canceled before capture, either by your server or through the Dashboard. |

## Payment Object

The following example shows the key fields returned in a Payment object. Use these fields to track transaction state, reconcile records, and attach contextual data.

```json
{
  "id": "pay_abc123xyz",
  "object": "payment",
  "amount": 4999,
  "currency": "usd",
  "status": "succeeded",
  "payment_method": {
    "type": "card",
    "card": {
      "brand": "visa",
      "last4": "4242",
      "exp_month": 12,
      "exp_year": 2027
    }
  },
  "description": "Order #8821 — Widget XL Blue",
  "idempotency_key": "order_8821_attempt_1",
  "settlement_id": "stl_7gHkLmN2pQ",
  "failure_code": null,
  "failure_message": null,
  "metadata": {
    "order_id": "order_8821",
    "customer_email": "jane@example.com"
  },
  "created_at": "2024-11-14T10:23:45Z",
  "updated_at": "2024-11-14T10:23:47Z"
}
```

<Note>
  The `amount` field is always expressed in the **smallest currency unit**. For USD, that means cents — so `4999` represents **$49.99**. For zero-decimal currencies like JPY, the value represents the exact amount (e.g., `500` = ¥500). Always convert before displaying amounts to customers.
</Note>

  </Card>

## Idempotency

Network failures and timeouts can cause uncertainty about whether a payment request was received and processed. To prevent accidental duplicate charges, pass an `idempotency_key` in the request header when creating a payment.

```bash
curl -X POST https://api.xpaylabs.com/v1/payments \
  -H "Authorization: Bearer sk_test_abc123" \
  -H "Idempotency-Key: order_8821_attempt_1" \
  -H "Content-Type: application/json" \
  -d '{
    "amount": 4999,
    "currency": "usd",
    "payment_method_id": "pm_card9xTz11"
  }'
```

When you supply an `idempotency_key`, XPayLabs stores the response for that key for **24 hours**. If you retry the same request with the same key within that window — for example, after a timeout — XPayLabs returns the original response without creating a new payment. This guarantees exactly-once semantics for payment creation.

<Accordion title="Idempotency key best practices">
  - Generate keys that are unique per logical operation, not per HTTP request. Tie them to your internal order or transaction ID so retries use the same key.
  - Keys can be any string up to 255 characters. UUIDs (`a1b2c3d4-...`) or prefixed identifiers (`order_8821_attempt_1`) both work well.
  - Do not reuse a key for a genuinely different payment. If an earlier payment with that key succeeded, XPayLabs returns the original successful payment instead of creating a new one.
  - Idempotency keys are scoped to your API key. The same key used with different API keys creates separate records.
</Accordion>

## Metadata

The `metadata` field lets you attach up to 50 key-value pairs of your own data to any Payment object. XPayLabs stores and returns this data as-is and does not use it in payment processing. Metadata is a convenient way to correlate XPayLabs payments with records in your own database without maintaining a separate mapping table.

```json
{
  "metadata": {
    "order_id": "order_8821",
    "customer_id": "cus_00124",
    "customer_email": "jane@example.com",
    "product_sku": "WIDGET-XL-BLU",
    "region": "us-west"
  }
}
```

Keys and values must both be strings. Values are limited to 500 characters each. You can update metadata on an existing payment with `PATCH /v1/payments/{id}` without affecting its processing state.
